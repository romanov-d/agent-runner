# agent-runner

Очередь запусков агентов на PostgreSQL и раннер к ней.

Задачу выполняет ровно один исполнитель. Воркер шлёт пульс, брошенные задачи
возвращаются в очередь, ошибки повторяются с нарастающей паузой, остановка по
сигналу не тратит попытку. Каждый шаг агента пишется в журнал, расход на модели
считается по попыткам, права на инструменты выданы перехватом вызова.

Зависимость одна: драйвер `pg`. Ни брокера, ни Redis, ни ORM.

```
docker compose up -d db
npm install && npm run migrate
npm run worker        # в одном окне
npm run demo          # в другом
```

## Что здесь решается

Длинная работа агента не помещается в один HTTP-запрос. Она идёт минутами,
ходит во внешние сервисы, падает на середине и стоит денег. Значит нужны две
разные вещи, и их полезно не смешивать:

**Очередь** решает, что исполнять и когда. Она переживает перезапуск процесса,
падение машины и выкатку новой версии.

**Раннер** исполняет: собирает контекст, выдаёт инструменты по правам, крутит
цикл «модель думает - вызывает инструмент - получает результат», пишет журнал,
считает деньги и останавливается по лимитам. Раннер перезапуск не переживает,
и не должен.

## Что ломалось и как чинилось

Всё перечисленное случилось в проде, а не придумано для примера.

**Воркер умирал посреди задачи, задача висела в работе вечно.** Очередь не
знает, что процесс мёртв: строка так и числится `running` с чужим владельцем.
Добавлен пульс - воркер обновляет `locked_at`, пока работает. Сторож возвращает
в очередь всё, у чего пульса не было дольше порога, а при исчерпанных попытках
помечает упавшим, иначе такие задачи всплывают бесконечно.

**Модель отвечала, а разбор ответа падал - токены списаны, в учёте ноль.**
Деньги утекали незаметно, потому что расход записывался только при успехе. Теперь
есть отдельный тип ошибки, который несёт расход с собой, и он пишется в задачу
даже при провале попытки.

**Два воркера брали одну задачу.** Сначала захват был сделан как «выбрать
свободную, потом обновить». Между выбором и обновлением успевал влезть второй
воркер. Переделано в один `UPDATE` с подзапросом `FOR UPDATE SKIP LOCKED`:
строка блокируется на время запроса, остальные её пропускают, а не встают в
очередь на блокировке.

**Транзакции не работали на серверless-подключении.** Код с `BEGIN/COMMIT`
жил на обычном драйвере и ломался на HTTP-соединении с базой. Каждая операция
переписана в одну SQL-команду, и теперь переносится между драйверами без правок.

**Остановка выкаткой съедала попытку.** Процесс уходил по `SIGTERM`, задача
возвращалась в очередь с потраченной попыткой и после трёх выкаток умирала сама
собой. Добавлен возврат без списания: задача не виновата, что мы перезапустились.

**Агент, которому отказали в инструменте, терял всю работу.** Отказ выбрасывался
наружу и валил задачу вместе с уже потраченными деньгами. Теперь отказ
возвращается модели текстом: она узнаёт причину и выбирает другой путь.

## Очередь

Весь смысл в одном запросе:

```sql
UPDATE jobs SET
  status = 'running', locked_by = $1, locked_at = now(),
  attempts = attempts + 1
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'queued' AND run_after <= now()
    AND (deadline IS NULL OR deadline > now())
  ORDER BY priority, run_after, id
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
AND status = 'queued'
RETURNING *;
```

Подзапрос берёт одну строку и блокирует её. `SKIP LOCKED` велит остальным
воркерам пропустить занятое, а не ждать. Внешнее условие `status = 'queued'` -
страховка на случай, если строку успели забрать между подзапросом и обновлением:
тогда мы просто ничего не обновим.

`attempts` растёт в момент захвата, а не в обработчике. Воркер может умереть до
первой строчки обработчика, и попытка должна считаться потраченной - иначе
задача, убивающая воркер, будет убивать его вечно.

Остальное: приоритеты и время запуска, дедлайны, ключ идемпотентности на
постановку, отсрочка на время ожидания внешнего сервиса без траты попытки,
отмена и повтор, накопление расхода по попыткам.

Воркер можно сузить до отдельных видов задач или агентов - так держат разные
пулы под тяжёлое и лёгкое, не заводя ради этого вторую очередь:

```
KINDS=agent AGENTS=analyst,editor npm run worker
```

## Раннер и права

Инструменты выдаются по списку на каждого агента, отдельно на чтение и на
запись. Необратимые действия проходят через подтверждение человека. Секреты
вырезаются из журнала по имени поля.

```ts
const analyst = { name: 'analyst', allow: ['kv_get'], canWrite: false };
const editor  = { name: 'editor',  allow: ['kv_get', 'kv_set'], canWrite: true };
```

Права сделаны перехватом вызова, а не фразой в промпте. Инструкцию в промпте
можно переспорить другой инструкцией, список разрешённых имён - нельзя.

Пределы на шаги, на деньги и на время стоят в раннере и проверяются до того,
как счёт вырастет.

## Тесты

```
npm run test:unit   # без базы
npm test            # всё, нужна поднятая база
```

Модель в тестах - детерминированная заглушка со сценарием ответов: прогон не
требует ключей, сети и денег.

Два теста, ради которых всё затевалось:

**Конкуренция.** Двадцать воркеров разбирают сто задач. Проверяется, что каждая
досталась ровно одному и что счётчик попыток у всех равен единице. Подделать
`SKIP LOCKED` мокой нельзя, поэтому тест идёт на настоящем Postgres.

**Падение.** Поднимается настоящий процесс воркера и убивается двумя способами.
`SIGKILL` - задача возвращается в очередь, попытка потрачена. `SIGTERM` -
задача возвращается, попытка не потрачена. Разница между этими двумя строками и
есть корректная остановка.

## Пропускная способность

```
npm run bench
```

На ноутбуке с Postgres в докере, 8 воркеров, пустой обработчик:

```
постановка: 2000 задач за 971 мс (2060/с)
разбор:     2000 задач за 499 мс (4008/с)
одна задача: 0.25 мс на полный цикл захват-закрытие
```

Числа приведены не как рекорд, а чтобы было видно: узкое место такой очереди -
не она сама.

## Чего здесь нет

Изоляции агента в контейнере, веб-интерфейса, метрик наружу, мультиарендности.
Это каркас, а не платформа: добавлять их имеет смысл под конкретные требования,
а не заранее.
